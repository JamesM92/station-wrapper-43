# Station Wrapper 43: reference

Everything the README leaves out: the volumes and settings, each page, the sources and breaks, the YouTube conversion, and updating. Start with the [README](../README.md) and the [QUICKSTART](../QUICKSTART.md).

## After the first start: the first stations, and the web player

1. **The wrapper gets your files ready; FieldStation42's console builds the stations.** Within a few minutes of the first start the `farm` job fills `catalog/by-genre/` with tag folders of links to your media: one folder per genre (from your NFO files), one per TubeArchivist channel (with `TA_ENABLED=1`), shows with no genre under `Unclassified`, and a `bump/` folder (the channel mid cards) with the Station Wrapper 43 splash card (5 seconds, `sw43-splash.mp4`). Add your own channel mid cards there. Nothing is copied.
   **A brand new install already has two stations on air**: `Channel Guide` on channel 1 (the scrolling guide of every channel, with its default settings and no music; change its style, messages and music on the Stations page; `FIRSTRUN_GUIDE_STATION=0` turns it off) and `Test Pattern` on channel 2, a test card with a quiet tone, made by the container on its first start (the pre-rendered one-minute clip from `assets/` copied into `catalog/by-genre/Test Pattern/`, played on a loop by a FieldStation42 loop station, with seven days of schedule). Open the dashboard and you should see it playing: that proves the whole chain works. It is created once and only when there are no stations yet; delete it in the console and it stays gone, and `FIRSTRUN_TEST_STATION=0` turns it off.
2. **Make stations on the dashboard's Stations page** (`http://<host>:5004/stations.html`). **New station** asks for a name and channel number, and lets you choose what plays: split the day into time blocks and tick the lists (the tag folders above) each block plays from, or make a station that repeats one list all day. Pick the time slot length (5, 10, 15, 30 or 60 minutes: 5 suits a movie channel, since a movie is rounded up to the next 5 minutes instead of the next half hour), the channel mid cards list, whether commercials play, and where the breaks go: all at the end of the show, interrupting it (at its chapter marks or black frames, spread out if it has neither), or one in the middle. **Save and build** then builds its catalog and the first 7 days of schedule, and takes you to its schedule. The page makes the station *through* FieldStation42's console, so the console shows it too. A station the form can't represent faithfully (several day templates, overrides, sequences, web or guide stations) is shown read-only with a pointer to the console, never flattened. FieldStation42's own console (`:4242`, linked as "advanced" in the navigation bar, and it opens in its own tab) is still there for everything the form doesn't cover.
3. Open `http://<host>:5004`, the dashboard. **A station you add (here or in the console) appears on it on its own** (the dashboard reads the station configs, and the container restarts only the tuner when they change): every channel with what's on now, a snapshot of each, and system stats. Click a channel to open the player (`/watch.html`). The header's **Schedule console** link opens the console on port 4242. Arrow keys or the on-screen buttons change channel there; type a number and hit Go to jump directly. A channel number set in `config/tuner/config.json` wins over a station that claims the same number.

   **If the picture freezes**, the page now notices that it has stopped moving (or that the server closed the stream) and reconnects on its own, with a message, instead of needing a refresh. A viewer whose connection can't keep up with the stream is dropped by the server and logged (`a viewer was dropped`), then reconnects.

   **Read-ahead for slow shares.** The tuner starts a new ffmpeg for each file the moment it is due, and each has to open its file over the network share first, which can take seconds. For each channel being watched, the **next** thing to play is copied into a **RAM disk** before it is due, and playback uses the copy: while a show plays, the next commercial break (the whole break, before it starts); while a break plays, the next episode; and the show itself if it comes back after the break. It learns how long each share takes (the delay to the first bytes and the sustained speed, on the pessimistic side, kept in `config/prefetch-stats.json`) and starts early enough for the file's size. It copies one file at a time per share, never uses more than `PREFETCH_MAX_MB`, never drops a copy that is playing, and falls back to the share when there is no room. The share is only read, and nothing is written to a drive. The compose file gives it a `tmpfs` RAM disk (`PREFETCH_CACHE_SIZE`, 6 GB by default; it counts against the memory you give Docker or its VM). **To use a folder on disk instead of RAM**, remove the `tmpfs` line, mount a local folder, and set `PREFETCH_RAM=0` and `PREFETCH_DIR`; **to turn it off**, set `PREFETCH=0`. Without a RAM disk (or a disk folder you chose) it stays off and the log says why (`[prefetch] off: …`). The dashboard's **Read-ahead** card shows what is cached and each share's speed, and a file that takes more than 2 seconds to start is logged (`took 4.2s to start (from the share)`).

   **Volume:** a slider sits beside the mute button; the left and right arrow keys change it and `M` mutes. The picture starts muted (browsers won't play sound until you touch something), and the first unmute comes up at the volume you last chose, which is remembered.

   **Captions in the web player.** When the show on air has captions, a **CC** button appears beside the mute button (or press `C`): it cycles through the tracks, then off. They come from a subtitle file next to the video with the same name (`Show - 01.srt`, `Show - 01.en.vtt`, `.ass`; a language in the name, like `.en.` or `.jpn.`, labels the track) or from a text subtitle track inside the video, which is how most anime releases carry theirs. Picture subtitles (DVD, Blu-ray) can't be shown. Captions are off until you turn them on, and your language choice is remembered, so they stay on from one episode to the next (`/watch.html?ch=7&cc=on` opens a channel with them on). The page works out the right line from the clock, so if they run early or late for you, use the **−** and **+** buttons beside CC (your setting is remembered). Nothing is added to the video stream, so **IPTV clients (Jellyfin, Plex, VLC through the HDHomeRun emulation) don't get captions yet**: that needs the subtitles put into the stream itself, which is on the list for later.
   **Captions on the IPTV stream.** The language is set once, on the Stations page (*Captions*; English by default). A video's captions in that language (a `.srt`, `.vtt` or `.ass` file beside it with the language in its name, such as `Show - 01.en.srt`, or a text track inside it) are then carried in two ways. *As a track:* every station sends them in its stream as a CEA-608 caption track, which players such as VLC and many TVs list under their captions button and can switch on and off; a station's page has a box to turn that off. Latin letters only (608's limit), and not every player shows them: Jellyfin's apps do not list an embedded caption track on live TV. *On the picture:* a block of a station's calendar has *Draw the captions on the picture while this plays*; where it is on, the captions are drawn into the video itself (always visible, in every player), which is what to use for a show you need subtitles for, such as a Japanese one, while English shows on the same channel stay clean. Other languages are never used in place of the one chosen, commercials and cards are left alone, and a subtitle that is a picture (DVD or Blu-ray) can't be used. The web player's CC button is not offered while the captions are on the picture, so they are not drawn twice.

On a new install there is no schedule yet: FieldStation42 creates its schedule database when the first station gets one, not at start-up. The dashboard still starts, with every channel off air, and the console is where you build the first station.

## Layout and conventions

**Three volumes make it work: config, catalog, and media.** The first two are local folders under one root, `FS42_LOCAL_ROOT`, and that is what you copy, back up and move. Your media stays on the NAS.

```
$FS42_LOCAL_ROOT/                  <- local disk, never an SMB share
  config/                          ONE volume: everything the container keeps
    runtime/                         FieldStation42's schedule database and sockets
    confs/                           station configs
    tuner/                           the dashboard's config.json (the container creates it)
    groups.toml                      your channel-building settings, if you use them
  catalog/                         ONE volume: everything made of symlinks
    by-genre/<Tag>/...               the tag folders FieldStation42 schedules from
    tanfo/<folder>-nfo/              one readable view per TubeArchivist library, once you switch the conversion on
    media-links/                     the pool: a symlink for every video (see "The pool")
$FS42_MEDIA_ROOT/                  <- your NAS: the videos themselves, read-only, ONE volume
```

Host paths come from `.env` (see `.env.example`):

| volume | where | why |
|---|---|---|
| `config` (`/config`) | `$FS42_CONFIG_ROOT`, default `$FS42_LOCAL_ROOT/config` | the sqlite schedule database, station configs, the dashboard's config. **Local disk**: sqlite misbehaves over SMB/NFS |
| `catalog` (`/app/catalog`) | `$FS42_CATALOG_ROOT`, default `$FS42_LOCAL_ROOT/catalog` | the folders of symlinks FieldStation42 schedules from. **Local disk, not an SMB share** (see below) |
| `media` (`/mnt/media`) | `$FS42_MEDIA_ROOT` | your actual show/commercial/channel mid card files, read-only. The only thing that belongs on the share |

FieldStation42 itself looks for `runtime/` and `confs/` next to its code, so the container links `/app/runtime` and `/app/confs` into the config volume when it starts. Nothing for you to do.

### Media: the whole share, several shares, or only some folders

- **Everything under one folder** (the default): set `FS42_MEDIA_ROOT` to it. The volume is a *recursive* bind, so if your NAS shares are mounted *inside* that folder on the host (`/mnt/media/tv` from one NAS, `/mnt/media/movies` from another) they all appear in the container. A plain bind would silently leave them out, so the compose file asks for the recursive kind. The read-only setting covers the nested shares too. (Checked on this project's Docker: a nested mount was invisible with a plain bind, visible with `rbind`, and not writable either way.)
- **Only some folders**: use one volume per folder, each mounted at `/mnt/media/<folder>` read-only (`/mnt/media/youtube`, `/mnt/media/anime`, `/mnt/media/movies`). Only those are visible; anything else under `/mnt/media` on the host is not. `docker-compose.yml` has a commented block showing how. Keep each folder at the same path inside and outside. The generator's libraries are the folders named `tvseries`, `anime` and `movies`.
- The catalog holds real folders; only individual video files in it are symlinks. Your media folders are *not* linked into it as whole folders (that sent a file manager straight into the media). An older install's whole-folder links (`catalog/anime -> /mnt/media/anime/`) are removed on container start. To get links to copy from, turn on `SYNC_ENABLED=1`: the pool is real folders with a link per file.

### Symlinks and SMB shares

The catalog is made of symlinks, and SMB/CIFS shares are bad at them: creating one can be refused, and an absolute link target can be followed on the server's side instead of yours. So the rule is:

- **Symlinks live on local disk. Media can live on the share.** A link that sits on local disk and points at a file on the share is ordinary file access, because the container's own mount resolves the path. Only the *media* has to be on SMB.
- That is why the catalog and the pool are on local disk, under `FS42_LOCAL_ROOT`, and not on the NAS. `FS42_CATALOG_ROOT` can move the catalog, to another **local** path.
- A TubeArchivist view built by TA_NFOWriter is also a folder of symlinks. If your media root is a share and the view sits in it, build the view on local disk (`ta_nfo.py --view-dir "$FS42_VIEW_ROOT"`) and mount it with `examples/docker-compose.view.example.yml`: copy it to `docker-compose.override.yml` and set `FS42_VIEW_ROOT` in `.env`. It mounts that folder read-only in the container at the same path as the host. If the view must stay on the share, mount the share with the cifs option `mfsymlinks` and test.
- `./setup-dirs.sh` checks first: it refuses a database folder on a network share, refuses a catalog or pool that can't hold a working symlink, and notes one that works but sits on a network share.
- `scripts/init.py` and `scripts/build_channels.py` both test the catalog (and `init.py` the TV libraries): they make a real symlink to a file outside the folder and follow it. If that fails, the generator stops before changing anything and says why. If it works but the folder is on a network filesystem, you get a note, because a link that works on the host can still resolve differently inside a container.
- **The container enforces it.** At start-up, `station-wrapper-43` checks `/app/catalog`. If it is on an SMB/CIFS share, or a test symlink can't be made and followed, it logs why and **exits with status 78 instead of running broken**. Docker will keep restarting it, so look at `docker logs station-wrapper-43`: the message names the fix. The same check protects the pool and the TubeArchivist view. On NFS and similar it only prints a note. To start anyway on a share you have tested, set `FS42_ALLOW_NETWORK_CATALOG=1` in `.env`.
- `docker-compose.yml` says the same at the top and at the volume. `FS42_LOCAL_ROOT` is required, so an unset one stops `docker compose` with a message rather than becoming an empty path. (It was called `FS42_SSD_ROOT`: the message says to rename it.)

**Moving an existing install into this layout.** There have been two earlier layouts. In the first, `runtime/` and `catalog/` sat directly under `FS42_SSD_ROOT`, `confs/` was on the NAS under `FS42_NAS_DATA`, and two containers ran (`206_fieldstation42` and `206_fs42-tuner`). In the second, everything sat under `FS42_LOCAL_ROOT/fs42/` with `media-links/` beside it. Rename the variable in `.env` if it is still `FS42_SSD_ROOT` (`sed -i 's/^FS42_SSD_ROOT=/FS42_LOCAL_ROOT=/' .env`) and let the script do the move:

```
docker compose down            # with the OLD compose file, if you still have it
./setup-dirs.sh --migrate      # MOVES the folders into config/ and catalog/ (a rename on the same disk, nothing copied),
                               # COPIES confs/ from the NAS if that is where it was (the original stays),
                               # and clears Docker's leftovers: old containers, and volumes with old paths or options
docker compose pull && docker compose up -d
```

It will not touch an older layout unless you pass `--migrate`: starting with an empty `config/runtime` would silently throw away your schedule, so without the flag it stops and says so. Your channel numbers live in the dashboard's config, which moves with the rest. If your catalog was on the NAS (the first layout allowed it), it is not moved: links there may be broken anyway. Regenerate it with `scripts/build_channels.py` (every station's catalog is rebuilt once).

**Why the script also looks at Docker.** Docker remembers a bind-style named volume's path *and options* when it first creates the volume. If either later changes (a new layout, or you move `FS42_LOCAL_ROOT`), `docker compose up` quietly keeps the old ones, or stops with a confusing `no such file or directory` mount error, and containers from an earlier set of services show up as "orphans". The media volume is the sharp case: its path is unchanged but it is now a recursive bind, and the old plain one would silently leave out nested shares. `./setup-dirs.sh` checks for exactly this and tells you what to run; `--migrate` does it. Removing such a volume only deletes Docker's note of the path: the folder it pointed at, and everything in it, is left alone.

**A note on who owns what.** The services run as `PUID`:`PGID` (unset: whoever owns your `config/` folder; a new or root-owned one is given to 1000:1000), so the folders and files they create inside `config/` and `catalog/` (`runtime/`, `tuner/`, `media-links/`, `tanfo/`) are that user's. Set `PUID` and `PGID` to your own account (`id -u`, `id -g`) and the scripts you run on the host (`init.py`, `build_channels.py`, `fs42_link.py`) can edit all of it. The first start after upgrading from a root-running version gives whatever root left behind in those two folders to that user, once. The image deliberately does not contain `/config` or `/app/catalog`: if it did, Docker would copy their owner (root) onto your folders the first time they are used. `docker exec <container> fs42-channels ...` also runs as that user.

The three volumes are bind-style named volumes (`driver_opts: {type: none, o: bind, device: ...}`), which is why `setup-dirs.sh` has to create the host directories up front -- unlike a plain short-syntax bind mount, this style won't auto-create a missing source directory, and `docker compose up` fails outright if it's missing instead.

Stack and container name: `station-wrapper-43`.

## The pool: a symlink for every video, and how to use it

`catalog/media-links/` mirrors your media as folders of symlinks: one link per video (and its `.nfo`), each pointing at the file on the share by the path the containers see. It is on local disk, so you can browse it with an ordinary file manager and take links from it **without touching the share and without writing a container path by hand.** Nothing is duplicated: a link is a few bytes.

The optional **sync** service (it runs inside the same container) keeps it current:

```
# .env
SYNC_ENABLED=1                   # then: docker compose up -d
# SYNC_INTERVAL_MINUTES=60       # how often it looks for new files
# SYNC_INCLUDE=tvseries,movies   # only some top-level folders of the share (or SYNC_EXCLUDE)
```

- **It only adds.** Each pass adds a link for every video that has none. It never removes or rewrites one, so a renamed or deleted file leaves its old link behind until you prune (`SYNC_PRUNE=1`, which removes only links to files that are gone). Treat the pool as managed: copy out of it, don't rearrange it.
- **It is gentle on the share.** A folder whose modified time hasn't changed isn't listed again (one `stat` instead of a listing). A folder changed within the last few seconds isn't trusted either, because a file added in the same instant would leave its time unchanged; it is simply looked at again on the next pass. A full walk happens once a day (`SYNC_FULL_EVERY_HOURS`) in case your server doesn't update folder times. Posters, subtitles and NAS junk folders (`@eaDir`, `#recycle`) are ignored.
- **It refuses to run on an SMB share**, like the other containers.

**Putting videos into a tag.** Copy links from the pool into `catalog/by-genre/<Tag>/`. A copy has to stay a *link*: `cp -a`, `rsync -a` and Linux file managers keep it as one, but a plain `cp`, or dragging a file over an SMB re-share to Windows, can follow the link and copy the whole video. So use the helper, which only ever makes links and refuses a real file:

```
docker exec station-wrapper-43 fs42-channels link Comedy "/app/catalog/media-links/tvseries/Some Show"      # a whole show
docker exec station-wrapper-43 fs42-channels link commercials /app/catalog/media-links/ads/1986/spot.mp4    # one video
docker exec station-wrapper-43 fs42-channels link Comedy <links...> --dry-run                               # look first
```

(`station-wrapper-43` is your container's name. The paths are the container's: the pool is `/app/catalog/media-links`.)

A tag is just a folder, so a new name makes a new tag. Don't re-export `catalog/media-links/` over SMB.

**Seeing the new videos.** FieldStation42 only learns of a video when its station's catalog is updated. The wrapper does that **without touching the schedule** (the **Update videos** button, or this job): the days already scheduled stay exactly as they are, and the new videos are used the next time days are added, which the schedule keeper does each morning. So `fs42-sync` also watches the tag folders: it logs which stations need an update because their tags changed (it matches a station to a tag by the tag name anywhere in the station's config). By default that is all it does. To have it done for you, set:

```
SYNC_REBUILD=1                   # on by default (0 turns it off)
SYNC_REBUILD_HOUR=4              # local time; it updates once a day, within SYNC_REBUILD_WINDOW_HOURS (default 2) of this
```

It updates only the affected stations' catalogs, and leaves their schedules alone. A failed update is retried on the next pass, and the first run only records a baseline (existing tags are not "changed"). A whole *folder* linked into a tag is noticed when the link itself changes, not when new files appear inside it: press Update videos on that station by hand.

## Known limitations

- **Desktop browsers only.** The portal uses [mpegts.js](https://github.com/xqq/mpegts.js) over MSE for lowest-latency live playback. Safari has no reliable MSE support for raw MPEG-TS, so iPhone/iPad/Apple TV can't play it. Adding phone/TV support means adding an HLS output alongside the MPEG-TS fanout (segmenting, playlists, per-viewer HTTP polling) -- real additional work, not a config flag, and isn't built.
- **Clock drift is fatal.** Both containers mount `/etc/localtime`. If the two disagree about the time, the tuner streams the wrong programme.
- See [`fs42-tuner/README.md`](fs42-tuner/README.md) for the rest -- encoder/viewer limits, late-joiner behavior, seek artifacts, and the Jellyfin/NextPVR/Sonarr integrations that stay in the code (off by default) if you ever want to layer them on.

Almost nothing needs setting: the defaults work, and what you would change is in the dashboard. A few advanced variables (`TA_ARGS`, `FARM_ARGS`, `KEEPER_FIRST_DELAY_SECONDS`, `FS42_CONSOLE`, …) exist for testing and unusual setups and are listed in the source.

## The login

The dashboard's **management pages** (Stations, the station form, Schedule, Lists & files, and the YouTube panel) and every `/api/…` call are behind a password. It is **on by default**: the first time you open one of those pages it sends you to a "set a password" page. Whoever opens it first sets the password, so do it right after the first start (or give the container `DASHBOARD_PASSWORD` to set it without the page; it is only used if no password has been set yet).

- One password for the whole dashboard (no accounts). It is stored salted and slow-hashed in `auth.json` in your config folder, never in clear. A login lasts 30 days in a browser cookie that scripts can't read and other sites can't send. **Password** in the navigation bar changes it (which logs everyone out); **Log out** ends the session for good, not just in that browser. Six wrong passwords in five minutes from one address are refused for a while.
- **What stays open on purpose:** the dashboard home with the channel list, the player, and the HDHomeRun and guide endpoints that Jellyfin and other clients use, because those clients can't log in. They show and play your channels; they can't change anything.
- **What it does not cover:** FieldStation42's own console on port 4242 is a separate program with no login of its own. Don't publish that port to the internet (remove `4242:4242` from the compose file if you don't use the console), and use a VPN for remote access.
- Behind your own login or reverse proxy? `DASHBOARD_LOGIN=0` switches this one off. Forgot the password? Delete `auth.json` from the config folder and restart the container: the next visitor sets a new one.

## Jellyfin shows the tuner but no channels or guide

Jellyfin asks the container for `/discover.json`, then fetches the channel list from the `LineupURL` inside it, and each stream from the lineup's URLs. Those addresses must be ones **Jellyfin** can reach. If `advertise_url` in `tuner/config.json` was never set (it starts as `http://localhost:5004`), the container now uses the address Jellyfin itself used to reach it, so adding the tuner as `<host>:5004` just works; set `advertise_url` only to force a particular address. Check from the machine (or container) Jellyfin runs on: `curl http://<host>:5004/lineup.json` should list your channels, and `curl http://<host>:5004/discover.json` shows the `BaseURL` and `LineupURL` it hands out. The guide is a **separate** provider in Jellyfin: Dashboard > Live TV > TV Guide Data Providers > + > XMLTV > `http://<host>:5004/xmltv.xml`; then run **Refresh Guide** (Dashboard > Scheduled Tasks) and check the channels under Live TV > Channels. Jellyfin's log names the failing address if it can't fetch one of them.

## One source for everything: this container

The rule for the whole system: **everything goes through this container**, so there is one authoritative lineup and one guide, and Jellyfin (or any other IPTV client) needs only this container as its tuner and its guide. Your own channels, an antenna tuner, playlists and cameras all appear in `/lineup.json` and are streamed from `/auto/v<number>`, and `/xmltv.xml` is the one guide for all of them. Add an antenna tuner on the **Sources** page (not as a second device in Jellyfin, except in its *guide only* mode): its channels keep their numbers, are played through the container, and the tuner's real listings (SiliconDust's guide, with episode names) are put on those same channels in our guide, so the guide channel, the dashboard and Jellyfin all show the same thing. In Jellyfin: one tuner (`<host>:5004`, type HDHomeRun) and one XMLTV guide (`http://<host>:5004/xmltv.xml`); remove the real HDHomeRun from Jellyfin's tuner list. A tuner can also be set to **Guide only**: its channels are not in the lineup or played here (so Jellyfin takes them straight from the tuner), but its real listings are added to our guide and the TV guide channel under the tuner's own channel numbers, which is how Jellyfin lines them up with its own copy of those channels. A playlist whose first line names a guide (`url-tvg="..."` or `x-tvg-url="..."`) gets real listings: the guide is read with ours and its programmes are put on the playlist's channels by their `tvg-id`; the feed's other channels are left out. Use the default **Convert** mode for sources a browser must play; **relay** is cheaper for clients that can play the antenna's MPEG-2 themselves. (The older single `passthrough` setting is retired: at start the container moves it onto the Sources page by itself and removes it from the config file, so the section below is only history. The `direct` mode is gone: clients always play through the container.)

## The Status page, diagnostics and the M3U playlist

**Status** (`/status.html`, in the navigation bar) lists what is wrong first (the console can't be reached, a station has no schedule or ran off air, a source can't be read, the media folder is empty, low disk, a slow guide build, ffmpeg missing), then each station, the versions inside the image, the guide, sources, encoders, viewers, CPU, memory and disk. **Test media speed** reads part of a video from your share and reports MB/s: a slow share is the usual reason for slow catalog builds and seeking. **Download diagnostics** saves one text file with all of this and the container's last messages (passwords and tokens are left out): attach it when asking for help. The same data is at `/api/system/status`.

`/lineup.m3u` is the lineup as an M3U playlist for TVHeadend and other IPTV software. Each entry's `tvg-id` is the channel's id in `/xmltv.xml` (`fs42.<number>`), `tvg-chno` is its number, and `group-title` says where it comes from. In TVHeadend: Configuration > DVB Inputs > Networks > add an **IPTV Automatic Network** with `http://<host>:5004/lineup.m3u`, then map the services to channels. TVHeadend needs `advertise_url` (or the address you used) to be one it can reach, not `localhost`. The guide goes in through an XMLTV grabber script that prints `http://<host>:5004/xmltv.xml`; this part is untried against a real TVHeadend.

## Backup, restore and upgrading

Everything that is yours lives in the three volumes: `/config` (settings, stations, schedules, `sources.json`, the catalog database), `/app/catalog` and `/mnt/media`. To back up, stop the container and copy the config folder (and the catalog folder if you want to skip a rebuild). To restore, put the folders back and start the container. To upgrade, pull the new image and recreate the container (`docker compose pull && docker compose up -d`); your folders are untouched. Passwords in source addresses are kept in `config/tuner/sources.json`, so keep the backup private.

## An HDHomeRun antenna tuner

A real HDHomeRun is a source on the **Sources** page (next section): **Add a source**, type *another HDHomeRun tuner*, its address (`http://<its IP>`), and a mode:

- **Converted for browsers** (the default): its channels join your lineup, numbered as the tuner numbers them (20.1, 20.2...), and are played through this container, re-encoded to H.264 and AAC like every other channel. Jellyfin needs only this container as its tuner.
- **Passed on as it is**: the same, with the video copied untouched. Cheap, but antenna video is usually MPEG-2, which a web browser can't play.
- **Guide only**: the channels are not in this container's lineup and are not played here. Only their listings are put into the guide, so your Jellyfin keeps its own tuner entry for the antenna and plays it from the device itself.

In Jellyfin add one tuner of type HDHomeRun at `<this Docker host's IP>:5004` and one XMLTV guide at `http://<this Docker host's IP>:5004/xmltv.xml`. That feed carries your channels and the antenna's. For *guide only* also add the antenna itself as a second HDHomeRun tuner (at its own address) and give it no guide provider of its own: Jellyfin can't read an HDHomeRun's schedule itself, and this container already has it. In the other modes, remove the real HDHomeRun from Jellyfin's tuner list so the two don't clash.

The antenna's listings (titles, episode names, synopses, pictures) come from SiliconDust's guide service, read with the device's own token, so there is nothing to sign up for. How far ahead they go depends on what SiliconDust return for your device (without an HDHomeRun DVR subscription it is usually a short window), and it covers over-the-air in the US and Canada. The answer is kept for three hours (also on disk, so a restart does not ask again) and the service is left alone for half an hour when it refuses, so the guide is not asked for on every build.

Tried against an HDHomeRun FLEX 4K: it found the device and its channels, relayed a channel's stream, and built the guide. Its channels' closed captions survive the re-encode, so a player that shows a caption track shows the antenna's.

An older `passthrough` entry in `tuner/config.json` is moved onto the Sources page when the container starts, and the setting leaves the file. Its `direct` mode is retired: a device's channels are always played through this container.

## IPTV sources: cameras, playlists and other tuners

The **Sources** page (`/iptv.html`, in the navigation bar) manages external IPTV sources: **another HDHomeRun tuner** (its address, such as `http://192.168.1.20`; its channels keep their own numbers), **a playlist** (an `.m3u` / `.m3u8` address, one channel per entry, read again every six hours or with **Read the channels again**) and **a single stream** such as a camera (`rtsp://`, `http://`, `rtmp://`, `udp://`, `rtp://` or `srt://`; a password in the address is kept in `config/tuner/sources.json` and never shown again).

Each source's channels get numbers of their own (from 100, 200, 300... or a first number you choose; a channel keeps its number even when others come and go; a number that is already taken is moved and the page says so), and you can switch a channel off, rename it or give it another number in the table under the source. The channels then join the lineup (for Jellyfin and other IPTV clients), the guide (`/xmltv.xml`, one "Live" programme each), the web player and the **dashboard**, where each shows an **IPTV external source** badge and the source's name. They are played through this container: **Convert** (the default) re-encodes to H.264 and AAC like every other channel, so a web browser can play antenna video (MPEG-2) and cameras; **Pass on as it is** copies the stream untouched, which is cheap but a browser may not play it. A stream is only opened while someone is watching, shared between viewers, and picked up again a few seconds after it drops. **Test the address** looks at a camera for a few seconds and says what it found. Switching a source off, or removing it, takes its channels out of the lineup, the guide and the player. `DASHBOARD_EDIT=0` makes the page look-only.

Tried against a real HDHomeRun FLEX 4K (its six channels read, numbered 20.1 to 20.6, 20.1 played as H.264/AAC in the web format, and its real listings, 373 programmes with episode names, appeared on those channels in `/xmltv.xml`), and with a playlist and a stream served from the same machine. 

## The Stations and Schedule pages

- **Stations** (`/stations.html`): every station as a card with its channel, the lists it plays, and whether it is on air. A card warns when less than a day of schedule is left, or shows that it is off air because the schedule ran out. **Edit** opens the form; **Rename** renames it (FieldStation42 keeps a station's schedule under its name, so the old schedule is cleared and a fresh catalog and 7 days are built under the new name, which takes a moment; any kind of station can be renamed, and it keeps its channel number and every setting); **Schedule** opens its schedule; **Add 7 days** extends the schedule without touching the catalog; **Update videos** brings videos you have added into the catalog and leaves the schedule alone, so the days already scheduled (say a week) are not thrown away: the new videos are used the next time days are added (the keeper does that every morning); **Rebuild schedule** is the heavy one (if the server is restarted while one is running, the card says the rebuild is not running any more, keeps playing the old schedule, and offers **Resume the rebuild**, which carries on instead of starting over: if the catalog had finished building it is kept and only the days not yet built are added; if it had not, the catalog build starts again, and the videos FieldStation42 had already read are remembered): it throws the schedule away and builds a new one from scratch (the page asks first; the channel keeps playing the old schedule until the new one is ready); **Delete** removes the station (never your lists or media).
- **The guide channel.** Choose **A scrolling guide of every channel** as the station type to get the classic TV guide channel: a modern blue grid of what is on every channel for the next few hours (the schedule's channels and any other guide source you've set up; a channel with nothing listed is left out), with the programme on air now lit, a line for the time now, the channels scrolling up when there are more than fit, the show's name as the big text with the time range under it and, when the episode names are switched on (see below), the episode's name in the same small type after the time (`8:00 – 8:30 PM · The Pilot`), any name too long for its slot scrolling along it (each rests a moment, then moves all the way round; the speed is set so every moving name goes through its cell twice while the rows scroll up once, so they are all in step, and the rows slow or speed it with the scroll speed; when everything fits and nothing scrolls up a calm pace is used), and your messages scrolling along the bottom. You set its title, its **style** (Modern blue, Midnight, Classic cable, Emerald or Sunset), how many hours it shows (2 to 6), the scroll speed, the messages, and **background music**: a folder (or one file) inside your media, which plays every mp3, flac, ogg, m4a, wav or opus file in it, shuffled, over and over (leave it empty for no music). FieldStation42's own guide channel needs a screen, so the tuner draws this one itself: nothing to schedule or build, it is on air as soon as it is saved, it uses an encoder only while someone watches (it draws at 15 frames a second, `GUIDE_FPS`), and it appears on the dashboard, in the player's channel list and in the IPTV lineup like any other channel. The picture is made with Pillow and DejaVu fonts, both in the image.
- **Better break points** (a tick box on a station's form, off by default). Breaks come, best first, from an **`.edl` file beside the video** (`Show S01E01.edl` next to `Show S01E01.mkv`, as Comskip, Kodi and MythTV write them: each `start end action` line with action 0 or 3 starts a break at `start`; the media folder is only ever read, so we read these and never write one), or from the chapter marks moved onto real scene changes, as follows. Every result is kept in our own store, `config/break-store.json` (the marks as the file had them, and the ones in use), so it survives a catalog rebuild. For a station that interrupts the show, FieldStation42 puts the breaks at the chapter marks in each video, and those marks are often well off the real scene change (a minute early or late). With this on, after the catalog is built or updated each mark is moved to the nearest black frame or stretch of silence within 90 seconds (`BREAK_SNAP_WINDOW`); a black frame with silence over it wins, a plain pause is the last resort, and a mark with nothing near it stays put. It never leaves a piece of programme shorter than 20 seconds. Each video is read once (the first build is slower, at low CPU priority) and the result is remembered in the store, so later updates only look at new or changed videos (and a changed `.edl`). It edits only the `chapter_points` table of FieldStation42's database (the one place the wrapper writes there). Days already scheduled keep their old breaks; **Rebuild schedule** or newly added days use the moved ones. To go back to the marks as the files have them, untick the box, clear the marks with FieldStation42's `--reset_chapters` and delete `break-store.json`. FieldStation42 still builds the schedules, from the marks put in its `chapter_points` table; a planner of our own that reads the store directly is the next step.
- **Several sources for a mid card or a commercial, and a YouTube channel's kinds of video.** Lists are for files you want to re-use, but a slot, a mid card or a commercial block never needs one: **Add…** more than once and a series, a season, an episode, a list and a YouTube playlist are put together as one source (a hidden list of its own, kept up to date; the same members are the same source). Inside a YouTube channel the browser also offers **All standard videos**, **All shorts** and **All streams**, so you don't have to pick each year's season: new seasons of that kind are followed as they appear (TA_NFOWriter keeps them in `Season 2026`, `Season 12026` and `Season 22026`). A YouTube playlist (`<library>/Playlists/<name>`) is a choice like any other, and a converted library's playlists are the first folder in it, shown as `_Playlists` (the folder keeps its name on disk). The YouTube converter card no longer has a "make lists from playlists" step: a playlist is added where it is used, the way a series is, or put in a list from the file browser on the same page. On the Lists & files page, opening a YouTube channel shows **Add all standard videos / shorts / streams** and **Use … as a source** for the kinds it has, the same choice as in the calendar's browser. A set is a source list of its own (named like `Ads + 2 more`); one you stop using stays there until you remove it on the Lists page.
- **Easier to start.** The dashboard shows a **Getting started** card until the first channel is on air (media found, a list with videos, a station, a build, then the Jellyfin address), with a button to the next step and **Hide**. A new station can **Start from** a template (a movie channel with 5 minute slots, one list all day, **a cartoon channel** (young kids early, teens mid-day, family in the evening, adult cartoons after 10 pm) and **a mainstream channel** (morning show, mid-day talk shows, a cartoon block, prime time, late night), each a full week laid out by time of day with a list of its own named for each part (made when the station is saved, and fine to leave empty: a slot whose lists have no videos yet plays the test pattern until they do), and a shuffled loop) that lays out the week for you. Under the form, a line says in words what the station will play and warns about lists with no videos. Leaving the form with changes that were not saved asks first. On the Status page, each warning has a button to the page that fixes it.
- **One click.** With no station yet, the **Getting started** card on the dashboard (and the empty Stations page) has **Make me a channel now**. It plays the biggest list with videos (not the mid cards or commercials), or, with no list yet, the first series, folder or movie in your media, all day, in 30 minute slots, with no commercials and no mid cards, on the first free channel number from 3 up, named `My Channel`; then it builds a week and says when it is on air, with a **Watch it** button and **Change it** to open the form. Each station stays independent: nothing is shared between stations except a list, if you choose to reuse one.
- **Pictures from the video itself.** A programme's picture is made when Jellyfin first asks for it: the cover art embedded in the video file (an MP4's `covr`), else a frame ten seconds in, kept 640 pixels wide in `config/art-cache` (never beside your media), one picture for a whole series (its poster if the show has one, else the first video asked about) and one for each movie, so a long-running show is one picture, not one per episode; the 500 most recently used are kept. At most two videos are opened for this at a time, so a guide of hundreds of programmes does not read hundreds of videos at once, and a video that cannot be read falls back to the show's poster.
- **The guide is made again when a build finishes.** The guide used to be rebuilt only on its own timer, so a station built a minute ago could be missing from the TV guide channel (and from Jellyfin's guide) for up to an hour. The guide is now made again as soon as a station's build is done.
- **A channel with nothing on is still in the TV guide.** The guide channel lists every channel, and one with nothing scheduled in the hours it shows has a single **Off air** cell across them, so a station is never missing from the grid just because its programmes are later in the day.
- **A test pattern says why.** Whenever a channel shows a test pattern, the reason is written in its bottom right corner: `NO FILE: <name>` (the scheduled video is not there), `BAD FILE: <name>` (it is there but nothing can be played from it), `NO COMMERCIAL` or `NO BUMP` (a break could not be filled, so the be-right-back card is held, because the station's commercials or mid cards lists have no videos), `QUEUEING` (the schedule has not reached this time yet: the next part is still to be built) and `OFF AIR: NOTHING SCHEDULED` (a slot with no list). The container log has the same lines, and the dashboard's now-playing says `Test pattern: <reason>`.
- **Off air is not a programme.** Time with nothing scheduled (the test pattern, which FieldStation42 calls "Offair", including hours whose lists have no videos yet) is left out of `/xmltv.xml`, so Jellyfin shows a gap, not a programme called Offair in its lists. The Schedule page still shows it.
- **Upcoming programmes in Jellyfin.** Jellyfin builds its Upcoming, Movies, Sports, News and Kids lists, and the picture beside each programme, from the guide, so each programme carries what it needs: its synopsis, its picture (the thumbnail beside the video; else the cover embedded in the video file, which is where TubeArchivist puts its thumbnail; else a frame taken from the video; else the show's poster) and categories Jellyfin recognises (`Movie` for a movie, `Kids` for animation, cartoons and family shows, plus the `.nfo`'s own genres such as `Sports` or `News`). How far ahead it can list is how far the schedule is built.
- **Channel logos.** Each of your channels carries a logo in `/xmltv.xml` (its `<icon>`), so Jellyfin shows one beside it after its next Refresh Guide. With nothing set, one is drawn from the channel's number and name (a colour of its own from the name; `/logo/<number>.png`). To use your own, put a picture (`.png`, `.jpg` or `.webp`, up to 2 MB) in your media folder and type its path under **Channel logo** on the station's form (`logos/cartoons.png`); the page warns when it can't be found. A source's channels (a playlist, a camera) use the logo their playlist names.
- **The guide says as much as a tuner's own.** Each of your own programmes in `/xmltv.xml` now carries what its `.nfo` has, as the antenna's listings do: the synopsis (`<plot>`), the aired date, its kinds (`<genre>`), its season and episode (both as `S01E05` and in XMLTV's own form, so Jellyfin shows them), and a picture (the `-thumb.jpg` beside the video, served from `/art/…` at the address the client reached us on). The episode's name was already there. A video with no `.nfo` still gets just its title; nothing is written to your media. Jellyfin reads the guide again at its next Refresh Guide.
- **Checked against the real engine.** `scripts/e2e-breaks.py` (a developer check, not CI; needs Docker and ffmpeg) runs the image with the repo's own code mounted over it and a few real tiny videos, and checks what FieldStation42 does with these settings: commercials off gives a block exactly the video's length with nothing around it; a commercials block opts its hours in with the default off; the default mid card starts a break and is used again at its end; a slot's own start and end cards (the `pre` and `post` folders) are used instead; and with the default cards off a break from a commercials block has no cards. All 14 checks pass.
- **A new commercials or mid card block starts empty.** Drawing a block on the Commercials or Mid cards tab no longer copies the block before it or the station's defaults: it says what is not chosen yet, and saving names the block that still needs something. Combined sources are numbered when two start the same way (`Ads + 1 more (2)`), and an error from the browser is shown in the browser panel where you are looking.
- **Empty hours and idle lists.** The Schedule page says when hours of a day play the test pattern because their lists have no videos yet (the default week or the season that applies). The **Sources made for stations** card on Lists & files also lists lists with no videos that no station names (a template makes one for each part of the day), each with **Delete**; the mid cards and commercials lists are never offered.
- **Duplicate, and sources in use.** **Duplicate** on the Stations page opens a new station that starts as a copy (its week, lists, commercials and cards), with a name and number to give it. The Lists & files page has a **Sources made for stations** card: every series, season, video, playlist or combined source a slot has used, which stations use it, and **Remove** for one nobody uses.
- **The station form uses the same browser.** **Default commercials** (the old "Breaks with commercials"), the default start and end of break **mid cards**, and what a "repeats one list all day" station plays (its **Shuffle the order** option is kept) are chosen with the same tree and take several sources: add a series, a season, a video, a list or a playlist more than once and they are put together as one source, as above.
- **Choosing what plays is one tree.** On the calendar, choosing what a slot plays (and its commercials and mid cards) opens a browser where **lists are folders like any other**: **Browse** has **Lists** and **Media**; open a list to see what is inside it, or open the media down through a folder, a series and a season, and **Add** (or **Use**, where only one is allowed) a whole list, a series, a season, a folder, or one video, wherever it is. Anything from the media, or a video or folder inside a list, becomes a source of its own the first time it is chosen (the same source the older show picker made), so no list has to be made first; a video inside a list is followed back to where it is in your media (when it is not inside the media view, it says so). A top folder of the media is not one choice: open it and choose inside. The station form's own default lists are still plain selects. Tried in a headless browser against a stand-in console.
- **Cards for one show or movie.** Click a video slot on the calendar (Videos tab): below its lists are **Mid cards for this show here**, a start-of-break list and an end-of-break list (choosing one sets the other to the same until you change it). So an hour of Rugrats can start its breaks with "this is Magic Station, we'll be back with more Rugrats after this" and end them with "back with more Rugrats". The slot's own cards win; if it has none, the **Mid cards** tab block for that hour is used; if there is none, the station's two default lists (when they are on). Choosing cards for a slot is the opt in for it. They are written as the hour's own bump folder, and apply to days built from now on. Unit-tested only. (FieldStation42's per-show `tag_overrides` can still be written by the form's API as `show_cards`, but the page no longer offers it: the slot is where a show's cards are chosen.)
- **Mid cards by time of day, and opt in.** The station form has **Default mid cards**, which is off for a new station: off, a break is commercials only (no card before or after), unless its time of day or its show was given cards, and giving cards there is the opt in for those videos; on, the two lists below it (start and end of break) are the defaults for every break that has none of its own. The calendar has a third tab, **Mid cards**, next to Videos and Commercials: draw a block over the hours and choose its start list and end list (they can be the same), and those hours use them instead of the station's defaults; hours with no block use the defaults. A pair of different lists is played from a hidden folder `catalog/by-genre/.cards.<start>--<end>` with `pre` and `post` links (made when the form is saved), shared by every station that uses the pair; the slot's own `bump_dir` points there. `wrapper_mid_cards: false` is the opt-out: the station's own bump folder becomes the hidden name `.cards.off`, and `fieldstation42/console_launch.py` asks FieldStation42 for a break without bumpers only when the break's cards are that default, so a block or a show that chose cards still gets them; a station made earlier keeps its cards. Applies to days built from now on. Unit-tested; the calendar tab has not been tried in a browser and none of it on the real engine.
- **Start and end of break mid cards.** The station form has two lists: the cards played at the start of each break and the ones played at its end (the same list is fine, and is what a station made earlier has). Two different lists are done with FieldStation42's own `pre` and `post` folders: the station gets a hidden folder `catalog/by-genre/.cards.<name>` holding two links, `pre` to the start list and `post` to the end list, and its `bump_dir` points there (`wrapper_start_cards` and `wrapper_end_cards` keep the choice). Like the other break settings it applies to days built from now on. Read from FieldStation42's code and unit-tested; not yet tried on the real engine.
- **A rebuild goes on past a block with no video.** FieldStation42 resets a show's place by reading the video of every scheduled block that has one, and a block whose video had left the catalog (it was rebuilt or changed since) stopped the whole rebuild with `'NoneType' object has no attribute 'path'`. `fieldstation42/console_launch.py` now leaves such a block out of that reading, so the rebuild carries on. Restart the container to start the console with it.
- **Soft slots (no breaks).** A time slot with no commercials is a soft target, not a wall: the next video is chosen from the lists of the slot the clock is in when the last one ends, whatever its length. A 2.5 hour movie in a 1 hour slot skips the next 1 hour slot and ends part way into the one after, and whatever that slot plays starts then, even if it will run past its end. Nothing is cut short and nothing is picked to avoid overrunning; a slot can be skipped whole when a long video covers it. This is the intended behaviour.
- **No breaks.** On the station form, **Default commercials** is off for a new station, which means no breaks, except in the hours where the calendar's Commercials tab names a list (choosing one is the opt in for those hours, even with the default off):  videos play back to back, the next starting the moment one ends, and the time slots are only a soft target that the day is filled to with videos from the lists (nothing is filled with commercials or channel mid cards). On, the spare time in each slot is filled from the commercials list you choose. It is `wrapper_no_breaks` in the station's config with the station's commercial folder set to the hidden name `.commercials.off` (so a slot that chose a list of its own can be told from the default), done by `fieldstation42/console_launch.py` like the next item, and it applies to days added from now on: use **Rebuild schedule** for days already scheduled. A station made earlier with commercials off is shown as "no breaks" and takes this the next time it is saved.
- **Short videos share a time slot.** FieldStation42 gives every video a whole slot, so an 11 minute video in a 30 minute slot spent the other 19 minutes on commercials. Now a video that fits more than once into the slot gets a block of the slot divided by how many fit: with 30 minute slots, an 11 minute video gets 15 minutes (two to the half hour), a 9 minute one 10 (three), under 7.5 minutes four, 6 minutes five, and 1 minute clips run back to back; only the time left over in each block is filled with commercials and channel mid cards, and the blocks always add up to the slot so the next one starts on the mark. A video that fills its slot is unchanged (a 22 minute show still gets 30). It is on for every station; the box **Fit short videos several to a time slot** on the station form switches it off for one (`wrapper_pack_short: false`). It is done by `fieldstation42/console_launch.py`, which starts FieldStation42's console with that one rule wrapped at run time (FieldStation42's own files are not changed; if its code has moved, the console starts unchanged and says so in the log, and the weekly compatibility check warns first). It applies to days added from now on: use **Rebuild schedule** to remake the days already scheduled. Tried on the real engine: three 11 minute videos made 15 minute blocks with 3.5 minutes of commercials each (18.5 with it off), 1 minute clips ran back to back, and a 22 minute video kept its 30 minute block.
- **Unassigned time plays the test pattern.** A week doesn't have to be filled to start: an hour with no slot is off air, and a standard station is written with `off_air_video` set to the test pattern clip (`assets/test-pattern.mp4`, colour bars and a quiet tone, shipped in the image at `/opt/assets/`), which FieldStation42 loops for those hours. A season with gaps falls back to the default week for them. Replacing a whole special day still has to cover the day. A station that already has its own `off_air_video` (set in the console) keeps it, and a station made before this needs **Save and build** once to get one. The pre-rendered clips in `assets/` (the splash card and the test pattern) are part of the repo and are loaded on a new install; see `assets/README.md`.
- **Names, not file names.** FieldStation42 names every video after its file. The guide (XMLTV and the guide channel), the now-playing banner and the schedule now use the name from the `.nfo` file beside the video, when there is one: an episode shows its show's name, a YouTube video shows its channel's name, a movie shows its title, and the episode's (or the video's) own title goes with it when the episode names are on (the default) (`tvshow.nfo`-style files written by the YouTube conversion and by most media tools). A video with no `.nfo` keeps its file name. **Show the episode's name too** on the guide channel's edit page (Stations > Edit on the guide) is a tick box to show the episode's name too (on by default; for a YouTube video it is the video's title, beside the channel's name): the guide channel and the XMLTV guide carry it apart (an XMLTV `sub-title`, small text after the time in the guide channel), and everywhere that has one line it reads "Friends: The One With The Pilot". It reads each `.nfo` once and remembers it for an hour (ten minutes when there is none), and it applies to what is already scheduled, with no rebuild.
- **Station form** (`/station.html`): name, channel number, type, then for a scheduled station the **schedule editor**: a week as a calendar (days across, half hours down). **Drag** on a day to draw a slot, **drag its top or bottom edge** to resize it (making it smaller only shortens it: the slot next to it does not stretch into the space, and a day that must be covered says what is missing until you fill it; making it bigger takes the time from the slot next to it), **drag the slot itself** to move it (to another time, or onto another day), **press Delete** to remove the selected slot, **Ctrl+C / Ctrl+X / Ctrl+V** to copy, cut and paste it (the paste lands with its top where the pointer is, on whichever day the pointer is over; with the pointer elsewhere it goes at the same time on the selected day), **click** it to choose what plays (one list, or several: it picks one at random each time), and use **Copy** and the **Weekdays / Weekend / All days** buttons to put the same slot at the same time on other days; the small buttons at the top of a day copy and paste a whole day. The **Videos / Commercials** tabs switch between what plays and which commercial list runs in each hour (commercials change on the hour, and only matter if "Fill the break time with commercials" is on). The smallest step is 30 minutes, and a slot that starts or ends at half past can hold only one list.
  - **Seasons.** The tabs **Default, Spring, Summer, Fall, Winter** each hold a week. The default week plays whenever nothing else applies; a season with "Same as the default schedule" ticked follows it, and unticking it gives that season a week of its own to edit. A season starts on the date you set (March 1, June 1, September 1, December 1 to begin with) and runs until the next one starts. This uses FieldStation42's own `week_overrides`, so each day gets the season it falls in when it is added to the schedule: no rebuild is needed at a season change.
  - **Special days.** The **Special days** tab holds one-off or yearly lineups, such as Shark Week or a Thanksgiving lineup. Each has a name and either certain dates (every year, or one year only) or a day like "the 4th Thursday of November" for however many days. It can have the same lineup every day, or a different one for each weekday. By default only the slots you draw change and the rest of the day plays as normal; tick **Replace the whole day** to fill the day yourself. A special day beats the season, which beats the default. (FieldStation42 cannot name 29 February.) Special days are written into the station's FieldStation42 config only while they are within about three weeks, and the keeper brings it up to date each morning, so a one-off day doesn't come round again next year.
  - **Next 14 days** under the calendar shows which layer (default, season or special day) wins each day.
  - **Days already scheduled are not changed by an edit.** FieldStation42 builds a day when it is added, so a new season or special day applies to days added from then on. To apply it to days already scheduled, use **Rebuild schedule** (the channel keeps playing the old schedule until the new one is ready).
  - A station's seasons, special days and commercial layer are kept by the wrapper (`config/schedules.json`) and written into the station's config. If you change such a station's schedule in FieldStation42's own console, the page shows it read-only (saving here would replace your console changes). A station made before this editor opens as its Default week. Where one block had several lists, it now plays one of them at random each time (earlier, two lists in one block split the hour between them).
  Also: where to name the station's own settings, the time slot length, channel mid cards list, commercials and break style, as before. To change a station's name use **Rename** on the Stations page. It refuses a clash with another station's name or channel, and lists that don't exist yet. Changing lists or times needs **Save and build** to take effect on the days already scheduled.
- **Schedule** (`/schedule.html`): pick a station and a day to see what is scheduled and what is on now, how far the schedule runs, and **Add 7 days**. It reads the schedule straight from the database FieldStation42 writes. **Click the arrow on a block** to see the files inside it, in play order with their times and kinds (program, channel mid card, commercial); a long block, such as a looping station's day, loads 200 at a time with **Show more**. Each file is shown by FieldStation42's own title for it when its catalog has one, with the file name beside it.
- **Keep schedules going** (the panel at the top of the Stations page, **on by default**): FieldStation42 only extends a station's schedule from inside its on-screen player, which this container never runs, so without this a station goes off air when its scheduled days run out. The keeper checks every 30 minutes. It keeps each station that already has a schedule built one day further than it shows: with 7 days chosen (the default; 1 to 30 in the panel) the pages show 7 days ahead and the schedule really runs 8. The extra day is added once a day, in the early morning (`KEEPER_TOPUP_HOUR`, 4 by default), so what you see is the same all day. A station with less than 12 hours left (for example after the server was off) is topped up straight away at any hour. It only ever *adds* days through the console, never rebuilds a catalog or clears anything; it skips a station you are building yourself, never starts a schedule for a station that doesn't have one yet, and leaves hidden stations alone. If a schedule ran out while the server was off, it catches up a month at a time. The panel shows when it last checked and what it last added. Everything that builds a day or a catalog (this page, the keeper, the first-start job, the channel tools, sync) takes turns through one lock, so two of them can't build the same day twice.
- **Dead links.** FieldStation42 stops a whole catalog build at the first video in a list that is no longer there (`FileNotFoundError ... by-genre/.../x.mkv`). Before any catalog is built or updated, the links in your lists whose video is gone are removed (a followed folder links it back if it returns). Nothing is removed when your media looks away (an empty or missing media folder, or most links dead at once), so an unmounted share can't empty your lists.
- Building runs in the background and the page shows its progress. Everything here goes through FieldStation42's console, which stays the one place a station's settings live. If the console is down the pages say so instead of failing quietly.
- All of this is behind the dashboard's login (see "The login" below), and `DASHBOARD_EDIT=0` makes it look-only even when logged in.

## The Files page: build your lists

FieldStation42's console has no folder or file browser, so the dashboard has one: **`http://<host>:5004/files.html`** (the **Lists & files** button on the dashboard). A *list* is a tag folder in `catalog/by-genre`, and a station plays from the lists you name in its schedule.

- **Left, your media**: browse your media (the pool, or the media folders when there is no pool), with each converted TubeArchivist library as a `<folder>-nfo` folder (read-only). Tick videos or whole folders.
- **Movies and shows in your media.** A folder that holds exactly one video and no season folders is a **movie**: it is listed as the movie file itself, without its folder, so you just tick the movie (extras and subtitle folders beside it don't matter, and neither do trailers, samples and Plex-style `-behindthescenes` extras). A folder with several videos, or with season folders (`Season 1`, `S01`, `Specials`...), is a **show**: it opens like any folder and is marked *show*. You don't need a list for each show: in a station's schedule editor, under the lists, **Add a series, season, episode or movie** is a set of choices that narrow one another: **folder** (each top-level folder of your media, such as anime, tvseries or youtube-nfo), then **series**, then **season**, then **episode**. A folder alone is not allowed. A series alone plays the whole series; with a season it plays that season; with an episode (or a movie picked as a series-level entry) it plays that one video, which is how a special day can show one movie or episode without a list made for it. Whatever you pick becomes a source on the spot (its videos are linked in the background, so a big series on a slow share doesn't hold the page up; the row says "linking its videos…" until it is done, and a build waits for it; the container log says how long it took), kept up to date as new episodes appear, and not mixed in with your lists (it is named after the series, or `series - season`, or `series - season - episode`; if a list already has that name the media folder goes in front). **Use as a source** on the Files page does the same ahead of time. **Stop using as a source** takes it away again (your media is never touched). A show can also go in a list (tick it like any folder) to make a pool of shows that a slot picks from at random; as a source of its own, in the Shows choice, it is played in order instead. A show is made as a hidden-marked list named after the folder, so a list that already has that name has to be renamed first. **A show in a schedule slot is played in order**: the slot is written with FieldStation42's own sequence tracking, so each airing (8 pm Monday to Friday, say) is the next episode, carrying on across days, seasons and special days, and starting over after the last one; new episodes are added to the end of its order without losing its place, and a rebuilt schedule picks up from the episode now on air. A slot that holds both a show and a list plays all of them in order, so keep them apart. A show added to a station that already has a catalog needs **Save and build** (or **Update videos**) so FieldStation42 can set up its place in the show.

**Mid cards drawn for a channel.** With *Default mid cards* on, the station form's *Also draw cards for this channel* gives the channel two cards of its own: *Station Wrapper 43* and the channel's name as 3D letters that turn back and forth, with *We'll be right back* (start of a break) or *We're back with more* (end) flat along the bottom, 5 seconds each. They are an addition: the start and end lists you chose stay, and a break picks from them and these like any other card. Nothing in your lists is changed. The two clips are kept in a hidden folder of the lists folder (`.generated-cards`), and the channel's break folder (`.cards.gen.<name>`, also hidden) links to them and to your lists. They are drawn in the background when the station is saved (about 20 seconds) and again after a rename or a change of design; deleting the channel removes them. If they cannot be drawn the station keeps playing its lists and its page says why. Letters the font lacks (such as Japanese) are drawn as boxes.

**Premiere nights.** On the calendar (Videos tab) select a block that plays one show and tick *New episodes premiere in this slot*, then choose where the new episodes start (a season or folder of the show, or one episode; everything before it is the older episodes). That block plays the next new episode each time it comes round (every Friday, if it is Friday's block of a Monday-to-Friday slot); every other airing of the show plays the older episodes in order and loops, including the ones that have already premiered. A night with no new episode left plays the loop, and until the first premiere has aired the show plays from its first episode as usual. A special day that replaces the premiere night does not use up an episode. Premieres count from the day the choice was made, and choosing another starting point starts over. The wrapper keeps hidden folders for this in the lists folder (`.loop.<show>` and `.new.<show>.<n>`, only ever added to); the schedule keeper makes them and brings them into the catalog each day as the nights come into range, so a night built several days ahead names a new episode that is already in the catalog.
- **Adding many things at once.** **Add to a list** runs on the server in the background, so picking a lot (say 17 YouTube channels, tens of thousands of links) doesn't hold the page up: the line at the top shows "Adding to ‘list’… Linking 4200 of 18000 files… (23s)" and the answer when it finishes (the page scrolls to it). One add can be up to 200,000 files (`FILES_MAX_LINKS`).
- **YouTube playlists and lists inside lists**: inside each `-nfo` folder in Media, a **Playlists** folder shows that library's TubeArchivist playlists. Tick one and **Add to a list** to link its videos into a folder named after it (kept up to date like any folder). Open a list and use **Put another list inside this one** to nest one list in another: it follows the inner list, so videos added to it, or taken out of it, show up in the outer list too (a list can't go inside itself or round in a circle). Renaming the inner list keeps the link; deleting it ends it and leaves the links that are there.
- **YouTube channels are not listed automatically.** The farm makes lists by genre only; a converted channel (or playlist) becomes part of a list when you add it. Lists an older version made per channel stay until you delete them. The playlists you tick in the YouTube panel still become lists of their own.
- **The video counts** beside each list on the Lists & files page come from a scan that checks every link, which takes minutes on a big library over a network share. It runs on a schedule (a minute after start-up, then every hour: `LIBRARY_SCAN_MINUTES`), and the pages only ever show what the last scan found, with how long ago that was. Opening a page never starts one. The last result is kept in `config/library-scan.json`, so a restart still has something to show. When you add to or take from a list, that one list is counted again straight away; the **Rescan** button above the lists scans everything now. A request that takes more than 3 seconds (`SLOW_REQUEST_SECONDS`) is logged as `[slow] GET /address took 12.3s`: `docker logs <container> | grep '\[slow\]'` shows what is slow.
- **A new station shows up on the dashboard about 8 seconds after it is saved.** The container restarts only the dashboard to pick up a new station, and it waits that long (`SUPERVISOR_SETTLE_SECONDS`) so the build that follows a save is never cut off by the restart. It also waits while a build is running.
- **A rebuild keeps the channel on air.** FieldStation42 deletes a station's schedule the moment a rebuild starts, so a long rebuild used to put the channel off air. Now the schedule that is still to come is copied aside first (`config/legacy-schedule.db`; FieldStation42's own database is never written), and the channel keeps playing it while the catalog and the new days are built. When the build finishes, the new schedule takes over at the end of the file that is on air at that moment, never in the middle of one, and the Stations page says when ("Playing the old schedule until 14:35, then the new one starts"). If the rebuild fails, the old schedule plays on until it runs out. The guide and the Schedule page show the two as one schedule. Renaming a station keeps its programming under the new name the same way. A station with no schedule yet has nothing to keep.
- **Keep folders up to date** (the tick beside **Add to a list**, on by default): a folder you add (a YouTube channel, a season, a whole series) stays followed. About every 30 minutes (`FOLLOW_INTERVAL_MINUTES`) the new videos that have appeared in it are linked into the list, with their `.nfo` files. It only ever adds links. Take a video out of the list and it stays out; take the whole folder out, or press **Stop** under *Kept up to date*, and it is no longer followed (links already there stay). Folders are remembered in `config/follows.json`. A single video is never followed, and untick the box for a one-time snapshot. New videos reach the schedule once the station's catalog is rebuilt (see `SYNC_REBUILD`).
- **Right, your lists**: create a list, pick it, and **Add** what you ticked. Open a list to see what is in it, tick items and **Remove from list**, **Rename list** or **Delete list**.
- **Nothing is copied.** Adding makes symlinks, so a video can be in any number of lists. A folder arrives as a real folder of links, so two shows' `S01E01.mp4` don't collide, and a video's `.nfo` comes along with it. Removing only removes links; your media is never written, and a real file in a list is never deleted (the page says so and leaves it).
- After you change a list, press **Update videos** on a station that uses it to see the change (it leaves the schedule alone); use **Rebuild schedule** only when you want the schedule itself redone. A renamed list must also be renamed in the station.

The page only changes things inside `catalog/by-genre`, and only accepts JSON requests, which a web page on another site can't send to it. It is behind the dashboard's login (below). `DASHBOARD_EDIT=0` (or `"edit": false` in the tuner config) turns the changing actions off and leaves browsing on.

## Even volume

Shows and commercials come at different loudness, so a break can be louder than the programme. The container measures each video
once (EBU R128 integrated loudness and true peak, audio only, in the background at low priority) and remembers the answer in
`config/loudness.json`. When the video plays, one fixed gain brings it to the target, with a limiter behind it for a stray peak.

- **Target:** set on the Stations page (*Volume*): -23 LUFS (broadcast television, the default), -20 or -16 (streaming).
- **Per station:** *Even out the volume* on a station's page, on by default.
- **Why a fixed gain:** a live compressor can't settle on a 30 second commercial and has no look-ahead after a join, and it flattens a
  film. A fixed gain changes how loud a video is and nothing else. A very quiet video is raised by at most 12 dB, and a video is
  never pushed so far that its peaks need more than 3 dB of limiting.
- **Not measured yet:** the video plays as it is, and is measured next (a video about to play goes to the front of the queue). The
  Stations page shows how many are measured. A new library is measured within minutes to hours, depending on its size and the share.
- **Not covered:** a live stream or an antenna channel passed on or converted from a source (they are not files), and a video with
  no audio.
- **Switching it off:** `LOUDNESS=0` for the whole container.

## Dead links and duplicates (the Lists & files page)

Above the lists, the Lists & files page shows how many videos your lists hold and flags two things, with the number beside the list they are in:

- **dead links**: the file a link points at is gone. This is judged from inside the container, which is the one FieldStation42 runs in, so a link that looks dead here is dead to it too. A dead link is left out of a catalog rebuild, so it does not stop one.
- **duplicates**: the same video linked more than once inside one list, which makes FieldStation42 schedule it more often. The same video in two different lists is fine and not flagged.

The scan is read-only, so it needs no extra access and changes nothing; **Rescan** forces a new one. The generator prints the same duplicate warning when it runs. To point it somewhere else, set `library_root` in `fs42-tuner/config.json`.

## Optional: let the wrapper create the stations (`fs42-channels`)

**You don't need this to get channels.** The console (above) is the normal way, and the farm job already prepared the files. These tools are for creating many stations in one go from your genres, and for putting links in tag folders by hand. **They run inside the container.** Nothing to clone or install on the host: `docker exec <container> fs42-channels init | build | link`, where `<container>` is your container's name. Inside, the catalog, the config, the manifest (`/config/groups.toml`) and the media paths are already known, and the generator adds each station's first day and restarts the tuner itself (no `docker` call). What it creates in the catalog is handed to the catalog folder's owner, so you can rearrange links from the host. The scripts are also in the repo (`scripts/init.py`, `scripts/build_channels.py`, `scripts/fs42_link.py`) if you would rather run them on the host, and every `scripts/build_channels.py ...` example below works as `fs42-channels build ...`.

New here? Run this once, after the container is up and before the generator. It writes nothing except a starter `groups.toml` (in your config folder), and it won't overwrite one.

```
docker exec station-wrapper-43 fs42-channels init
```

It finds your libraries (`tvseries/`, `anime/`, `movies/`, and any folder that is a TV library of its own, such as a TA_NFOWriter view with its playlists), checks that the FieldStation42 container can see them, and previews the channels the generator would make. The container check matters: the symlinks point into `/mnt/media/<folder>` as the container sees it, so every folder it will use has to be mounted there, or the links will point at nothing. It checks each folder it found one by one, so it works whether you share in the whole media folder or one volume per folder, and it names the folder that has no volume. It then writes `groups.toml` into the `config/` folder (beside `catalog/`) and prints the next two commands.

`groups.toml` holds every setting and group in one file, so a setup lives in your config folder instead of in shell history. It is TOML, which Python reads with nothing to install, and it allows comments. Command-line flags override it, and `--tv-library` and the group flags add to it.

```toml
media_root = "/mnt/media"
tv_libraries = ["/mnt/media/tanfo"]
# genre names to rename
[genre_map]
"sci-fi" = "Science Fiction"

[[group]]                      # a playlist becomes the commercials
playlist = "1980s Ads *"
to = "commercials"
[[group]]                      # a whole channel becomes its own channel, named after it
show = "Old Cartoons Channel"
[[group]]                      # one source, one `to`; --video needs `to`
video = "News/*[[]nnRYx_dfvoY]*"
to = "Retro Mix"
```

```
docker exec station-wrapper-43 fs42-channels build --dry-run
docker exec station-wrapper-43 fs42-channels build
```

(`build` reads `/config/groups.toml` by itself.) With a manifest in the `config/` folder, `--catalog` defaults to the `catalog/` folder beside `config/`, and the dashboard's config is found in `config/tuner/`. A typo in a key name stops the run with a list of the valid ones, so a misspelling can't silently do nothing.

## Building genre channels from the archive

`scripts/build_channels.py` makes one channel per genre from Sonarr and Radarr's NFO files. No AI is involved. Each show or movie goes under its first listed genre. Shows and movies with no genre are reported and skipped unless you pass `--include-unclassified`.

```
docker exec station-wrapper-43 fs42-channels build --dry-run
docker exec station-wrapper-43 fs42-channels build
```

It runs inside the container. It finds the dashboard's config (`/config/tuner/config.json`, which the container creates on first start), builds the stations through the console on `127.0.0.1:4242`, and adds each station's first day. When it has written the channels it signals the supervisor (PID 1 hands the signal on), which restarts **only the tuner**, so the new channels are live and the console is untouched. `--no-restart-tuner` skips that. Run on the host instead (`scripts/build_channels.py`, with `pip install defusedxml`), it does the same through `docker exec` and `docker kill` on the container named by `--fs42-container`.

Run it again whenever the archive changes. **It only ever adds.** `catalog/by-genre/` is a plain FieldStation42 content folder: tag folders of symlinks that point at your archive, never copies. Each run links the videos that are missing and leaves every existing link alone, so links you add, move or re-point by hand survive, and one video can sit in several tag folders at once. A station is created if it is missing and is never rewritten after that, so you can edit its config in FieldStation42. A station whose tag folder gained links gets its catalog rebuilt and a day of schedule added back; one whose folder didn't change is left alone. Hand-made stations and channels are never touched. Channel numbers are kept across runs.

Nothing is removed unless you ask: `--prune` removes links whose source video is gone from the archive, and only links that point somewhere the generator manages. A link you made to anywhere else is never touched. If a prune empties a genre completely, that station is left in place (rebuilding an empty catalog crashes FieldStation42), so remove it by hand.

### Which build is running

The last two `entrypoint:` lines of the startup messages, just above the `[supervisor]` lines (`docker logs <container> | grep -B1 -A1 'Station Wrapper 43'`), say what it is, for example `entrypoint: Station Wrapper 43 dev-f41d692 (commit f41d692, built 2026-10-05T03:10:00Z)` and `entrypoint: contains FieldStation42 ca585d3 and TA_NFOWriter v0.5.0`. A release shows its version number instead of `dev-<commit>`. The same values are on the image as labels (`docker inspect --format '{{ index .Config.Labels \"org.opencontainers.image.revision\" }}' <container>`). An image you built yourself with a plain `docker compose build` says `dev` and `unknown`: only CI passes the real values.

### Channel mid cards

FieldStation42 plays short clips (a channel ident, a "stay tuned") at the start and the end of each commercial break, and the generator stops without any: the **channel mid cards**. They live in the catalog volume, in a plain folder: **`catalog/by-genre/bump/`**. The container creates it the first time it starts, together with `catalog/by-genre/` (the tag folders FieldStation42 schedules from), and puts one clip in it (the 5 second Station Wrapper 43 splash card, `sw43-splash.mp4`, pre-rendered in the repo's `assets/` folder and copied from the image) so a station builds out of the box. Replace it with your own, or add more: real files are fine, they are small, and sub-folders are allowed. The new folders belong to whoever owns the catalog folder, so you can add clips from the host without `sudo`. The clip is only added when the folder is first created; delete it and it stays deleted. You don't need a media folder or an extra volume for bump clips.

If your media also has a `bump/` folder (the channel mid cards) and you mount it, its clips are linked into that folder as well; that is optional. A clip added later is picked up by stations the next time their catalog is rebuilt.

### TubeArchivist channels (switched on in the dashboard)

**No environment variables needed.** Open `http://<host>:5004/files.html`. The **YouTube (TubeArchivist)** panel at the top lists your library folders (folders holding `UC…` channel folders) with the number of channels found, and **Add** puts in another (detected ones are offered). Each library is converted into a view of its own and shows in **Media** as its folder name plus `-nfo` (`youtube` becomes `youtube-nfo`; two folders with the same name get `-2`), and the original is hidden there once its view exists. Tick **Convert my TubeArchivist library**, check the folders, and it starts within a few seconds. The panel then shows what it is doing, including **which channel it is on right now** ("Now on Some Channel (channel 123 of 480, 122 finished), 1,200 of 3,400 of its videos, last seen working a few seconds ago": TA_NFOWriter 0.5 reports a line per channel and a heartbeat every 30 seconds, which the page shows; on top of that it looks at the video file the converter has open every few seconds, so the name is there before the first heartbeat, and the line goes quiet only if it is stuck on one file), when it last ran and when it runs next, and a **Convert now** button; **Check for new videos** sets how often (15 minutes to a week, once a day by default). A folder that isn't there, or a conversion that fails, is shown in red with the reason. The setting is saved in the config volume (`settings.json`), so it survives restarts and takes effect without one. When a conversion finishes, the new channels get lists of their own (the farm job) and appear in the `-nfo` folders in **Media**.

**Playlists:** TubeArchivist's playlists are written to the converted library's `Playlists` folder (shown first, as `_Playlists`). There is no step on this panel to make lists from them: a playlist is chosen where it is used, the way a series is (a slot, a mid card or a commercial block on the calendar), or put in a list from the file browser on this page. Lists made from playlists by an earlier version stay where they are.

The older variables still work, as the *starting* values only; anything saved in the dashboard wins:


[TA_NFOWriter](https://github.com/JamesM92/TA_NFOWriter) reads the metadata TubeArchivist embeds in its videos and writes a readable library of channels: each channel a folder with a `tvshow.nfo` and `Season N/` folders of symlinked videos and NFOs, plus a `.m3u8` per TubeArchivist playlist. It is built into the container: switch it on and it runs on a schedule.

> **Only TubeArchivist videos with embedded metadata are converted into channels.** The import reads the metadata TubeArchivist writes into its own downloads. A video that lacks it (a plain YouTube download, a clip you added by hand, or another folder altogether) is not turned into a channel, a series or a playlist: it is shown in **Media** as the ordinary folder and file names, and you add it to lists and stations like any other folder.

```
# .env
TA_ENABLED=1
TA_LIBRARY=/mnt/media/tubearchivist     # the TubeArchivist library, as the container sees it (several: separate with commas)
# TA_INTERVAL_MINUTES=1440              # daily by default
```

```
docker compose up -d                     # the first run happens at start
docker exec station-wrapper-43 fs42-channels build --dry-run
```

Where things end up, and why that is the point:

- **The view is built inside the catalog volume** (`catalog/tanfo/<folder>-nfo`, one per library), which is local disk. The farm lives beside it in `catalog/by-genre`. All the symlinks in the system sit in one local volume, and the media they point at can be on your NAS.
- **The links use the container's own paths.** It runs inside the container that also runs FieldStation42 and the dashboard, and sees the library under `/mnt/media`, so a link to `/mnt/media/tubearchivist/UC…/id.mp4` resolves everywhere that matters. Your host's path to the TubeArchivist share can be anything. Running `ta_nfo.py` on the host, by contrast, writes host paths that the container then has to match.
- **The TubeArchivist library must be inside `FS42_MEDIA_ROOT`** (that is where it is found). If it lives somewhere else on your NAS, add a read-only volume for it to the service in your compose file and set `TA_LIBRARY` to its path there.
- **Tell the generator about the view** with the host folder and the container path: `tv_libraries = ["/your/catalog/tanfo/youtube-nfo=/app/catalog/tanfo/youtube-nfo"]` in `groups.toml` (one entry per library). `scripts/init.py --catalog …` finds it and writes that line for you.
- **The view belongs to TA_NFOWriter; the farm belongs to you.** It keeps the view in step with TubeArchivist (adds new videos, and with `--cleanup` removes links to deleted ones). Don't rearrange links inside `tanfo`: it would recreate them. A library you take out of the list has its view removed on the next run, and the flat `tanfo/<channel>` layout of earlier versions is cleaned up the same way. Move and group links in `catalog/by-genre`, which only ever gains links.
- Updating TA_NFOWriter: the image build downloads one pinned release (`TA_NFOWRITER_REF`) and checks its SHA-256, so a changed file fails the build. Bump the tag and the hash together in the `Dockerfile`.
- It refuses to run if the catalog is on an SMB share, for the same reason as the rest of the container; the log line `[ta-nfo] …` says so, and only it stops. If `TA_LIBRARY` isn't mounted it says that and stops too, without taking the console or dashboard down.

Running `ta_nfo.py` yourself on the host still works: build a view, pass it with `--tv-library HOST[=CONTAINER]`, and keep it on local disk (see `examples/docker-compose.view.example.yml`).

- `--tv-library HOST[=CONTAINER]` can be repeated and mixed with the default `tvseries`/`anime`/`movies` folders. Drop `--no-default-libraries` to keep those. `CONTAINER` is the path the containers see the folder at. It defaults to `HOST`.
- The farm link is `catalog/by-genre/<Genre>/<folder>-nfo/<Channel>/...`, with the view folder name as the library label. The label must not be `tvseries`, `anime`, `movies` or `bump`.
- Links chain: farm link, then the view's link, then the TubeArchivist file. The generator only checks the first step on the host. The rest are container paths that may not exist there, so it never follows them: the dead-link count on the Lists & files page checks the whole chain from inside the container.
- Subtitle files (`.vtt`) and images are not linked into the catalog. FieldStation42 doesn't use them.

#### Groups: send videos somewhere without moving them

A group takes videos from a source and adds them to another place, as symlinks. Nothing is moved or copied on disk, the videos also stay in their own genre channels, and one video can belong to as many groups as you like. There are three kinds of source, and you can mix them freely:

| option | source |
|---|---|
| `--playlist NAME` | a TA_NFOWriter playlist. TA_NFOWriter's `--playlists` writes one `.m3u8` per TubeArchivist playlist into `<view>/Playlists/`. `NAME` is the file name without `.m3u8` |
| `--show NAME` | a whole show, series or TubeArchivist channel, by folder name. It works for `tvseries`, `anime` and `movies` folders too |
| `--video PATTERN=DEST` | individual videos. `PATTERN` is matched against `<show>/<path inside the show>`, for example `"News/*[[]nnRYx_dfvoY]*"` (`[[]` is a literal `[`). `DEST` is required |

Every kind takes `NAME[=DEST]` (`--video` needs the `=DEST`), and can be repeated. `NAME` and `PATTERN` can be wildcards (`*`, `?`, `[..]`) and ignore case. Quote them so your shell doesn't expand them. `DEST` says where the videos go:

| `DEST` | what happens |
|---|---|
| none | its own channel, named after the playlist or show |
| a genre, e.g. `Comedy` | that genre's channel, in addition to the videos' own genre |
| `commercials` | the commercials every station plays between programmes. Stations then get `commercial_free: false` and a `commercial_dir`. These videos are the one exception to "also stays in its genre channel": they are not linked into the genre channels, because they would air as programmes |

```
scripts/build_channels.py --media-root /mnt/media --no-default-libraries --tv-library /mnt/media/tanfo \
    --playlist "1980s Ads *=commercials" \
    --show "Old Cartoons Channel=Saturday Morning" --playlist "Cartoon Picks=Saturday Morning" \
    --video "News/*[[]nnRYx_dfvoY]*=Retro Mix" \
    --catalog "${FS42_CATALOG_ROOT:-$FS42_LOCAL_ROOT/catalog}" --dry-run
```

- **One set from many sources.** Groups that share a `DEST` build one set, whatever their kind. Three playlists, a whole channel and a few single videos can all feed one commercials set or one channel. A video named by several of them is linked once into that set.
- **Several places.** A video in groups with different `DEST`s is linked into each of them. Group order doesn't matter.
- **Whole shows keep their files together.** A show sent somewhere takes its `tvshow.nfo` and season NFOs with it. A video's sidecar NFO always follows the video.
- A genre whose videos are all commercials gets no station.
- **A playlist is read as the starting list, not kept in step.** The first run links its videos in. If you later remove a video from the playlist, its link stays until you delete it or run `--prune` and its file is gone. Add a video to the playlist and the next run links it. The playlist itself is a snapshot from when TubeArchivist last embedded each video (see TA_NFOWriter's README).
- New commercials rebuild every station's catalog on the next run, and a day of schedule is added back. Stations that already exist get a `commercial_dir` filled in if they have none, and nothing else about them is changed.
- A genre can't be named `commercials`. Rename it with `--genre-map`.
- A name or pattern that matches nothing stops the run and lists what exists, so a typo can't silently drop videos. Run `ta_nfo.py --playlists` first so the playlists exist.

Tests: `scripts/test_build_channels.py`, `test_init.py`, `test_compose.py`, `test_setup_dirs.py` and `test_fs42_link.py` in `scripts/`; `test_sync.py` in `fs42-sync/`; `test_supervisor.py` in `supervisor/`; and the tuner's own in `fs42-tuner/`.

Not handled yet: episode order within a show. Episodes are scheduled from the genre folder, not as ordered sequences.

## Updating FieldStation42

`fieldstation42/src/` is an unmodified copy of upstream at the commit recorded in `fieldstation42/FS42_REF`. Don't edit it; it's overwritten on sync.

```
scripts/sync-fs42.sh              # re-sync the commit in FS42_REF
scripts/sync-fs42.sh <ref>        # move to a new commit or tag (updates FS42_REF)
docker compose up -d --build
```

Each sync prints what changed against the old copy, then runs `scripts/check-fs42-contract.py`. The check asserts the `liquid_blocks` columns and plan JSON keys that `fs42-tuner/resolver.py` reads. If it fails, the upstream schema has moved: update `resolver.py` to match, then rebuild. Don't deploy past a failed check.

`scripts/sync-fs42.sh` checks after you update. The weekly `upstream-compat` workflow checks before: it runs the same checks against upstream's newest commit, so a break shows up while you are still on the pinned version. It runs from the default branch (`main`) and needs a runner that can reach github.com.

The contract check reads source text, and covers both things this wrapper depends on: the schedule database the tuner reads, and the console routes, answers and CLI output the channel generator uses. A sync also runs the generator tests, which check the station configs it writes against FieldStation42's own `station_config_schema.json` (this needs `pip install defusedxml jsonschema`). So a FieldStation42 update that renames a route, a status value or a config key fails at sync time, not on the next generator run. None of this proves the schedule actually runs, so after a sync also rebuild a schedule in the web console and confirm the portal plays it.
